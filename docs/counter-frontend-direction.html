Counter v0.1.8 · frontend build direction

The backend is a shop. The till is a demo.

A read of the shipped plugin against COUNTERIMPLEMENTATION.md. The plan is sound and the PHP behind it is genuinely good. But the till screen — the one surface a shop representative touches all day — has five keyboard actions wired to empty functions, no way to search a product by name, no way to split a payment, and no way at all to bill a standing customer on account.

102 files 17 admin screens 5 F-keys stubbed 1 tender row max 0 DOM tests
The short answer

Is the plan OK? Is the plugin OK?

The plan Unusually good. Invariants, schema, per-task self-tests, and it explicitly called for the things that are missing. Not the problem.
The PHP backend Real work. Phone normalisation, credit limits, FIFO costing, ledger discipline, HPOS. Carefully commented and self-tested.
The till UI A shell. ~95 lines of innerHTML render the whole screen. Core interactions are empty function bodies.
wp-admin The earlier audit read this correctly — 9 back-office areas have no screen, and the nav is one flat list.

One correction to the earlier audit. It concluded that “the plan itself is fully built and self-tested” and that everything remaining is “the next phase, not a defect in what shipped.” That holds for the missing wp-admin screens. It does not hold for the till. Task P1.13 named F3, F4, F5 and F10 in a keyboard-map table, and P1.14 named split tenders in its own commit message. Those shipped as empty functions and a single-row form. That is a defect in what shipped, and it sits on the highest-traffic screen in the product.

The earlier audit looked only at wp-admin, so it never opened assets/pos.js. Everything below that concerns the till is new.

Root cause

Why the suite is green and the screen is hollow

Selftest.php is 490 KB — larger than the rest of the plugin put together — and it passes. It passes because of what it checks. The terminal's entire test, test_terminal_assets(), is five assertions:

#AssertionWould an empty F4 fail it?
1/pos/ does not return 404No
2HTML contains window.CNTR and the asset tagsNo
3pos.js contains no external hostNo
4pos.js contains no console.logNo
5Catalogue endpoint honours the terminal roleNo

Not one assertion invokes a UI interaction. The business-logic tests that do pass — split tenders, credit shortfalls, weight barcodes — reach the code through window.CNTR._pos, an export hatch at the bottom of the file that hands the test suite submitSale, searchByText and a dozen others directly. The tests call the functions. The screen never does.

The plan predicted this exactly. P1.13 says: “Manual — this is the bulk of the verification and cannot be done from a terminal”, and lists “Every key in the map, in order, on the real machine.” That manual pass is the only thing that would have caught this, and it is the one step a coding agent structurally cannot perform. The gap is not carelessness — it is the seam the plan itself flagged, landed on.

Two defects with no plan line, found in the same read

  • Focus is never restored. The only .focus() call in the entire file targets the print iframe. render() replaces root.innerHTML wholesale on every cart change, destroying and recreating the search input, and relies on the autofocus attribute — which does not reliably re-fire on re-inserted nodes. After a sale prints, focus is inside the iframe. Scanning still works (the scanner listens on window), but typing goes nowhere until the cashier clicks the box.
  • The cart rows are inert. Each <li> carries a data-idx and nothing listens for it. No row selection, no per-line remove, no quantity control, no line total, no tax or discount column — so “the selected line” that F3 and F4 are supposed to act on has no way to be selected in the first place.
Priority 1

Billing a standing customer

This is the stated first priority, and it is currently the widest gap in the product: a regular customer — the one who buys weekly, has a running বাকি balance, and may pay part now and part later — cannot be billed correctly from the till at all. Not awkwardly. At all.

The backend is finished and waiting

  • Pos\Customers::normalise() folds +8801711…, 8801711…, 01711… and 1711… onto one key, and rejects anything else rather than storing a mangled record.
  • Customers::lookup() returns every candidate for a phone, newest first — its own comment says “a household shares a number; the till shows a picker rather than guessing which one is right.”
  • Tenders::VALID_METHODS already includes 'credit'. A shortfall against an identified customer holding cntr_credit_sale is written as a real ledger debit.
  • CustomerLedger has check_limit(), balance(), record_payment(), aging() and statement(). The limit is checked before the order is created, and refuses with a readable message.

None of it is reachable. The tender dropdown offers cash, card, bKash, Nagad, Rocket, bank — credit is not in the list. The customer is attached by a browser prompt() that stores a raw typed string and never calls /customers/lookup. So resolve_customer() re-normalises server-side and silently takes matches[0] — the exact household guess the backend author wrote a picker comment to prevent.

What has to be added

Almost all of this is frontend. Exactly one backend addition is required, because the lookup endpoint returns identity only — cntr_customer_index holds phone_norm, customer_id, display_name, last_order_at and nothing else. The till cannot show what someone owes.

The flow to build

The tender screen, rebuilt

Rules the screen must enforce

  • The credit row is hidden entirely unless a customer is attached and the operator holds cntr_credit_sale. A credit sale to “walk-in” is meaningless — the backend already refuses it, so the UI should never offer it.
  • Warn before the server refuses. The profile response carries available; if the credit row exceeds it, mark the row and disable submit with the reason shown inline. check_limit() stays the authority — this is courtesy, not enforcement.
  • Remaining must reach zero before submit enables. Cash over the due becomes a change row automatically, as it does today.
  • Apply roundingStep to the cash row. It is already in window.CNTR and currently ignored.
  • Print the balance on the receipt. A credit customer should walk away holding what they now owe. Docs/Templates supports this; the receipt builder needs the line.

One architectural gap to raise before building, not after. Price tiers are bound to the register, not the customer: Groups::price_at_register() reads price_group_id out of the register's settings_json. There is no customer→price-group link anywhere in the schema — I checked every reference. So a wholesale regular who walks up to the retail till gets retail prices, and no amount of frontend work changes that. If “as per their need” includes their own pricing, that needs a schema decision — a price_group_id on the customer, overriding the register's when a customer is attached. I would not build it silently; it changes what a sale costs.

Priority 3

wp-admin — where the earlier audit was right

Confirmed by direct count: one add_menu_page plus sixteen add_submenu_page calls, all in one flat list, in registration order. Nine operational areas have no screen. That reading is accurate and its recommended order is sound — group the sidebar first, then locations and registers, then employees, then purchasing.

Two refinements to that plan:

  • Build the shared entity picker first, not seventh. The audit puts the reusable name-search component last. Every screen ahead of it — locations, employees, suppliers, purchase orders, transfers, stocktakes — needs to resolve a product, a supplier or an employee by name. Building it first means six screens consume it instead of six screens shipping raw ID fields and being retrofitted later.
  • A Settings screen is worth more than its position suggests. It is listed as “low daily-use frequency,” which is true, but pos.weight_barcode_prefix, pos.discount_ceiling_pct and cash.rounding_step all directly govern till behaviour. Once the till work above actually reads those values, they stop being dormant config and start being things a shop needs to change without SSH.
Sequence

Build order

  1. Blocking

    Close the verification gap first

    Add a DOM-level test path before writing feature code, or the next pass repeats this one. A headless page load of /pos/ that dispatches real key events and asserts on rendered output would have caught all five stubs. Chromium and Playwright are already available in this environment. Without it, “green” keeps meaning “the exports work.”

  2. Cart rows, focus, search results

    The foundation the rest sits on. Row selection makes F3/F4 possible; focus discipline makes the screen usable after any action; the result list makes the till operable by someone who does not have the barcode memorised.

  3. Priority 1

    Standing customer: panel, picker, profile endpoint

    The one new endpoint, the persistent customer panel, and the household picker replacing prompt(). Ends the silent matches[0] guess.

  4. Priority 1

    Multi-row tender with credit

    Split payment, the credit row, live remaining/change, rounding applied, post-sale balance shown and printed. This is the point at which a standing customer can actually be billed.

  5. F3, F4, F5, F10, held-sale list

    The remaining stubs. Each is small once step 2 exists, and each is capability-gated and audited on the backend already.

  6. Raise the pricing question, then the admin screens

    Get a decision on customer-level price groups before starting wp-admin, since it may add a column. Then the sidebar grouping, the shared picker, and the missing screens in the earlier audit's order.

Scope note

What this is and isn't

Steps 1–5 are not new scope. They finish P1.13 and P1.14 as those tasks were written, plus the customer-profile endpoint, which is the single genuinely new backend piece and exists only because the till needs to display a balance it currently cannot see.

Step 6 and the wp-admin work are new scope beyond COUNTERIMPLEMENTATION.md, exactly as the earlier audit described.

Nothing in here asks for the backend to be rewritten. The PHP is the reason this is a short list rather than a long one — the ledger discipline, the credit limits, the tender validation and the FIFO costing are all done and tested. What is missing is the surface a person puts their hands on.
